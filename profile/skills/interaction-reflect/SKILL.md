# reflect - Reflection & Improvement

## Intent and trigger

Learn from actual execution evidence after a task. Use when the user asks for a retrospective or repeated frictions are demonstrated.

## Procedure

1. Compare goal, result, cost, errors, corrections and surprises using available evidence; leave unavailable measurements unknown.
2. Distinguish a single incident from repetition.
3. Propose the smallest improvement at the code/tool/test/skill layer and a falsifiable validation.

## Output contract

Reflection summary and prioritized evidence-backed improvements.

## Boundaries and failure modes

Read `skill://af-interaction` for shared boundaries if not already loaded. Follow shared RULES.md, accepted project decisions, and native permissions. Do not rewrite global policy or skills automatically; avoid ungrounded self-criticism and reconstructed private reasoning. Reflection alone does not authorize durable context writes or implementing proposed improvements. Label observations, inferences, unknowns, and unexecuted checks separately. Keep answers proportional; advisors are optional for material specialist questions.

## Example invocation

- User: What should we learn from the previous implementation?
- Success: Identify attributable lessons and a small proposed improvement without silently changing policy or artifacts.
