# Check selection by changed boundary

Read only branches relevant to the request and choose the narrowest checks covering observable acceptance. Prefer installed project commands; resolve task-required project dependencies under RULES.md before reporting a missing capability. A still unavailable required check is NOT-RUN, not NOT-APPLICABLE. Avoid an automatic all-tools checklist or unrelated tool provisioning.

| Boundary | Main-agent verification | Evidence and failure paths |
| --- | --- | --- |
| Static/types/lint/build | Inspect manifests/config/CI and use project scripts/pinned local tools; resolve task-required project dependencies within verified scope under RULES.md. Include checks required by project policy or the affected path. | Exact argv/cwd/exit and diagnostics. Missing global/runtime capabilities remain NOT-RUN unless separately authorized; no relevant type/build target can be NOT-APPLICABLE with a reason. Project runners do not authorize unrelated/global tooling or browser/analysis installation. |
| Fix/debugging | Use the user report or existing failing test as repro; trace a falsifiable hypothesis. Add consumer-visible regression only if current coverage misses it. | Relevant failure before correction when already available, corrected behavior, boundary cases and unchanged contract. Do not rerun just to reconfirm the user's observation. |
| Unit/integration/consumer | Exercise the real CLI/API or integration boundary as well as relevant existing tests; use controlled fixtures. | Inputs, expected/observed outputs, errors/timeouts/cleanup. Mock-only tests cannot establish a real integration pass. |
| API/authentication | Request the real local endpoint using authorized fixture identities, validate status/body, unauthorized and cross-owner paths, invalid input and idempotency where relevant. | Never use production accounts or perform external mutations without exact authorization. Separate tenant partitioning from authorization. |
| Database/migration | Use disposable DB/schema/data matching the engine when available; check forward migration, constraint/query behavior, failure atomicity, and approved rollback or forward recovery. | Record engine/version/baseline, commands, actual persisted results, transaction failure and data-integrity checks. SQLite does not establish PostgreSQL/MySQL locking or dialect behavior. |
| Security-sensitive | Load af-security; threat-model the changed trust boundary and exercise focused negative cases with authorized local data. Reuse installed static/dependency scanners only when safe and permitted. | Reject/encode malicious input as applicable, ownership/permission checks, no secret output. Source advice is not a scanner result; no broad external scanning, exploit delivery or auto-install. |
| Performance | Load af-performance; measure the actual hot path on a fixed fixture before/after with runtime/environment/input/warmup/repeats and correctness checks. | Timings/distribution, allocations/memory or query plans when available, and noise limits. No claimed improvement without comparable measurements; no unstable timing threshold as the only correctness test. |
| Deployment/observability | Load af-operations; run local build/start/health/readiness/shutdown/failure checks and inspect meaningful logs/metrics. | A local image/config validation is not an actual deployment. External apply/release/migration requires approval. Redact sensitive logs and avoid production fixtures. |
| Browser/UI/accessibility | Follow browser.md on the actual changed page with Tern. | Interaction, resulting state, keyboard/semantics/focus, page errors and visual proof. State limits of automated accessibility and browser coverage. |

A successful check applies only to its tested artifact/inputs/environment. Link evidence to the task and current source state; old session evidence is historical. Changes after a check invalidate the affected result until it is rerun. Review with no subsequent implementation change does not require rerunning an unchanged check.
