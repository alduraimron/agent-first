# Improvement backlog

This is iterative improvement after the requested architecture, not permission to omit its components or add a new runtime. Evidence and limits belong in [Principles validation](../eval/principles-validation.md), the historical validation reports and the [correction ledger](corrections.md). Promote a change only at its owning layer with a falsifiable check.

| Observation or limit | Proposed improvement | Placement and completion evidence |
| --- | --- | --- |
| Reviewer yield schemas and transient tool arguments failed in prior runs, sometimes recovered and sometimes timed out | Compare native/provider versions and scoped handoff clarity on retained failing scenarios before another prompt change | Tooling/workflow; actual native tasks complete with valid output and no hidden aborted consultation; preserve failed history |
| In the normal-YOLO tenant run, the bundled reviewer executed Git despite a read-only assignment; main had supplied a summary rather than a literal patch | Validate the concrete verbatim-patch handoff, then assess native per-spawn built-in permission narrowing if hard enforcement is required | Workflow/native tooling; preserve the failed journal and require inspected, command-free native reviewer completion. A copied reviewer or global execution prompt would change the agreed design/autonomy and is not implemented |
| One model/scenario pass cannot establish routing/advice reliability | Add held-out real personal tasks and human scoring for options, evidence, constraints, finding disposition and approval judgment | Evaluation; repeated independent tasks with separate behavior/policy/reasoning scores |
| Basic Tern keyboard/semantic/visual checks are not full accessibility or browser compatibility | Add explicitly authorized assistive-technology, zoom/contrast and supported cross-browser checks when project needs them | Verification; actual device/browser/manual evidence, never an automatic downloaded runner |
| SQLite fixtures cannot establish PostgreSQL/MySQL locking, dialects, production backfills or large-data recovery | Add disposable engine-specific cases only when an existing or explicitly approved environment is available | Database/evaluation; actual migration/concurrency/rollback and representative-plan results |
| Local lifecycle checks are not a production release or restored backup | Exercise a separately authorized disposable deployment and restore path using the project's existing infrastructure | Operations; real health, shutdown, interrupted rollout/restore evidence and explicit target approval |
| Profiles/OVNFS do not contain hostile scripts or exfiltration | Specify a threat model before introducing OS/container/VM containment; do not imply prompt rules solve it | Architecture/security; explicit boundary decision and independently observed containment tests |
| Runtime/model upgrades may change loading, schema and permission behavior | Rerun relevant existing probes and held-out cases on deliberate upgrades, comparing exact versions and failures | Tooling; effective context/approval tests plus actual workflows on the new versions |
| Native Tern hosting can fall back to an owned engine, potentially downloading one before caller inspection | Seek a supported native require-existing-Tern/fail-closed option; until then preflight the live host and reject unexpected backends | Native tooling/verification; unavailable-host tests must fail without launching or downloading an engine, with explicit authorization for any new capability |
| Durable project files can drift when multiple independent sessions work on one task | Evaluate conflicting handoffs and explicit task ownership on disposable projects before any coordination mechanism | Context/workflow; conflicts are detected and reconciled without losing user work or historical evidence |
| The actual narrow Tern viewport overflowed on long markup-like text; basic validation needed a stricter helper assertion | Add explicit long-text/viewport acceptance when relevant; validate field-associated errors instead of arbitrary status text | Frontend/verification; actual screenshot/geometry and keyboard/error state, not a source-style assertion |
| The first principles batch omitted leaf URIs in several assignments, loaded one untriggered premise leaf, and missed a proof read; native chronology alone cannot establish good judgment | Track full-read compliance, trigger precision, missed/unnecessary selections and actual decision quality across held-out tasks/models; compare bounded baselines only when causal claims are needed | Evaluation; retain per-decision source/advice evidence, original failed runs and separate corrected parser replays alongside independent consumer outcomes; see [principles validation](../eval/principles-validation.md) |
| Trivial edits can attract unnecessary design exploration, tools or consultation | Retain negative-selection cases and assess whether proof alone, or at most one additional justified leaf, was sufficient | Selector/evaluation; minimal relevant reads, no gratuitous delegation/ceremony and correct consumer behavior |
| Native registry/manualSkills behavior is version- and environment-specific; filtered or unknown skills can be inaccessible | Extend fresh-session checks to deliberately unsupported names and broader already-available environments before claiming portability | Native configuration/evaluation; exact inclusion, 36 registry/12 visible entries on the supported version, direct URI resolution and honest inaccessible-skill uncertainty; no automatic install or fallback |
| Tenant local tests and a bundled correctness verdict passed while an independent nested-payload consumer detected data loss | Assess review misses against complete consumer contracts, especially payload preservation and nested ownership, rather than counting completed reviews | Workflow/evaluation; reviewer findings/disposition and independent counterexamples remain separate evidence, with the original failure retained |

No automatic policy rewrite, new specialist, external memory service, custom orchestration infrastructure, or Tern plugin follows from this list. Require repeated material need and a simpler-native-alternative comparison first.
